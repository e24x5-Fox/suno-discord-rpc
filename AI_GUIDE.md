# 🤖 Гайд для AI-ассистентов: Suno → Discord RPC

Этот документ описывает архитектуру проекта, типичные проблемы и как их решать.
Предназначен для будущих AI-сессий, чтобы не начинать с нуля.

---

## Архитектура проекта

```
suno.com (браузер)
  └── content.js        ← читает DOM страницы каждые 2 сек
        └── chrome.runtime.sendMessage(TRACK_UPDATE)
              └── background.js   ← WebSocket клиент
                    └── ws://localhost:6969
                          └── suno_rpc.py  ← WebSocket сервер + Discord RPC
                                └── Discord (pypresence / AioPresence)
```

**Поток данных:** DOM → content.js → background.js → Python → Discord

### Два источника активности: Suno и YouTube

К серверу параллельно подключаются ДВА расширения:
[suno-rpc-extension](https://github.com/e24x5-Fox/suno-rpc-extension) (Suno) и
[youtube-rpc-extension](https://github.com/e24x5-Fox/youtube-rpc-extension)
(YouTube). **Оба живут в собственных репозиториях, а не в этом** — правка
протокола затрагивает два репозитория сразу и одним коммитом не делается.
Различаются они полем `source` в сообщении
(`"suno"` / `"youtube"`); если поля нет, данные считаются суновскими — так
продолжают работать старые сборки расширения.

**Транспорты у них разные, и это не случайность.** Suno-расширение шлёт данные
по WebSocket на порт 6969 (ему нужен быстрый канал для аудио-данных FFT).
YouTube-расширение шлёт `POST /api/source_update` на control API (6972), потому
что должно работать и в Firefox — см. раздел «Грабли второго источника». Оба
транспорта заканчиваются вызовом одной и той же `process_source_update()`:
если правишь арбитраж или статистику, правь только её.

Расширения друг о друге не знают. Кто попадёт в Discord, решает
`pick_active_source()` в `suno_rpc.py`:

| Suno | YouTube | В Discord |
|---|---|---|
| играет | играет | Suno |
| пауза | играет | YouTube |
| закрыт/молчит | играет | YouTube |
| играет | пауза | Suno |
| пауза | пауза | тот, что играл последним |

«Молчит» — это отсутствие сообщений дольше `SOURCE_STALE_SEC` (10 с), а НЕ
разрыв WebSocket: расширение держит соединение открытым, даже когда ни одной
вкладки нет, поэтому факт подключения ничего не говорит о воспроизведении.

При смене источника `last_update` сбрасывается в 0 — иначе Discord до
`UPDATE_INTERVAL` секунд держал бы активность того, что уже не играет.

Что отличается у YouTube в `update_presence()`: тип активности берётся из
`youtube_activity_type` (по умолчанию Watching = 3), вторая строка — просто
название канала без приписки «by», `small_text` = «YouTube», кнопки читаются из
секции `[buttons_youtube]`, а статистика — из `youtube_stats`.

**Шапка активности — это глагол типа плюс `name`, а не имя Discord-приложения.**
По умолчанию Discord подставляет туда имя приложения, к которому подключён RPC,
и под роликом с YouTube было написано «Смотрит Suno AI». Поле `name` в
`SET_ACTIVITY` это переопределяет — второе Discord-приложение заводить не нужно.
Проверено по ответу Discord на SET_ACTIVITY: клиент возвращает активность в том
виде, в каком её принял, и `"name": "YouTube"` в ответе сохраняется. Значения
берутся из `app_name` (Suno, по умолчанию пусто = имя приложения) и
`youtube_app_name` (по умолчанию «YouTube»); пустая строка означает «не слать
name вовсе», а не «слать пустое имя».

**Статистика у источников раздельная.** `suno_stats.json` — музыка,
`youtube_stats.json` — видео; смешивать их в одном топе пользователь не хотел.
Пишутся обе ДО арбитража и независимо от него: если музыка играет, а видео
параллельно доигрывает, просмотр всё равно засчитывается — то, что его не видно
в Discord, к статистике отношения не имеет.

**Отчёт при этом один на двоих.** `youtube_stats.generate_html()` переиспользует
`_HTML_TEMPLATE` и функции секций из `suno_stats` (формат записи специально
совпадает: `title` = название видео, `artist` = канал, `cover` = превью,
`url` = ссылка), а затем меняет шапку и подсовывает блок переопределения стилей
с красной палитрой. Перекраска сделана именно отдельным `<style>` в конце
`<head>`, а не заменой цветов по тексту: фирменный оранжевый захардкожен в
шаблоне четыре десятка раз, в градиентах и тенях, и ловить каждое вхождение
строкой — гарантия что-нибудь пропустить.

Страницы `suno_stats.html` и `youtube_stats.html` лежат рядом и ссылаются друг
на друга кнопкой в шапке (`suno_stats.nav_button()`) — обычной относительной
ссылкой, поэтому переключение происходит внутри одного окна без всякого IPC.
`generate_stats_html(page)` пересобирает ОБЕ страницы: иначе переход по кнопке
открыл бы соседнюю в том виде, в каком её оставили в прошлый раз.

### Два процесса: интерфейс и бэкенд

Приложение состоит из Electron-фронтенда и Python-бэкенда — это два отдельных
процесса, и Electron главный:

```
desktop/ (Electron, главный процесс)
├── трей, меню, окно «Suno RPC», окно статистики
└── spawn → python/suno_rpc.py --watch-stdin   (headless, без единого окна)
      ├── WS   6969  ← расширение Chrome
      ├── WS   6970  → Broadcast API (оверлей и прочие подписчики)
      ├── HTTP 6971  ← мобильная синхронизация (0.0.0.0, доступен по сети)
      └── HTTP 6972  ← control API (ТОЛЬКО 127.0.0.1)
```

До августа 2026 интерфейс был встроен в Python: сначала tkinter, потом
pywebview (`webview.create_window` + класс `Api` как `js_api`), трей — на
pystray, иконка рисовалась в PIL. Всё это удалено; `python/requirements.txt`
теперь состоит из трёх строк. Разметка интерфейса переехала из
`python/web_ui/index.html` в `desktop/src/index.html` практически без правок.

**Control API (6972)** — то, чем интерфейс управляет бэкендом. Маршруты 1:1
повторяют методы класса `Api` в `suno_rpc.py`: `/api/get_state`,
`/api/get_config`, `/api/save_config`, `/api/reconnect_discord`,
`/api/disconnect_discord`, `/api/get_logs`, `/api/get_stats_summary`,
`/api/generate_stats_html`, `/api/quit`, плюс `/api/ping` для проверки
готовности. Цепочка вызова из окна выглядит так:

```
index.html  →  window.sunoApi.get_state()      (preload.js, contextBridge)
            →  ipcRenderer.invoke('get_state')
            →  main.js: ipcMain.handle
            →  HTTP GET 127.0.0.1:6972/api/get_state
            →  Api.get_state() в suno_rpc.py
```

Добавляя метод, правь все четыре места: `Api` в `suno_rpc.py`, маршрут в
`start_control_server()`, `ipcMain.handle` в `main.js`, строку в `preload.js`.

Состояние трека опрашивает **главный процесс Electron** раз в секунду и
рассылает в окно через `webContents.send('state', …)`. Рендерер сам ничего не
опрашивает: иконка в трее должна обновляться и при свёрнутом окне, поэтому
опрос всё равно нужен в main, а второй опрос из окна был бы дублированием.

## Селекторы DOM на suno.com (актуальные)

### Название трека
```js
// aria-label содержит "Playbar: Title for <название>"
const titleLink = document.querySelector('a[aria-label^="Playbar: Title for"]');
const label = titleLink.getAttribute('aria-label');
const title = label.match(/Playbar:\s*Title for\s+(.+)/i)?.[1]?.trim();
```
⚠️ `.textContent` ссылки не равен названию — название только в `aria-label`.

### Обложка трека
```js
// img с aria-label "Playbar: Cover image for <название>"
// src = https://cdn2.suno.ai/image_b54c84cc-....jpeg?width=100
// data-src = https://cdn2.suno.ai/image_large_b54c84cc-....jpeg  ← лучшее качество
const coverImg = document.querySelector('img[aria-label^="Playbar: Cover image"]');
const dataSrc = coverImg.getAttribute('data-src');   // большое изображение
const src     = coverImg.getAttribute('src');         // маленькое (width=100)
const coverUrl = dataSrc || src.replace(/\?.*$/, "");
```
⚠️ Не использовать `.src` (свойство) — может вернуть пустую строку в контексте расширения. Использовать `getAttribute('src')`.

⚠️ На странице много `img[src*="cdn2.suno.ai"]` — это список треков, **не** обложка плеера. Нужен именно `aria-label^="Playbar: Cover image"`.

### Исполнитель
```js
// Вариант 1: ссылка с aria-label
const artistLink = document.querySelector('a[aria-label^="Playbar: Artist"]');

// Вариант 2: второй span.line-clamp-1 в зоне плеера
const spans = document.querySelectorAll('span.line-clamp-1.w-full');
const artist = spans[1]?.textContent?.trim();
```

### Аудио-элемент (прогресс-бар)
```js
const audio = document.querySelector('audio');
audio.currentTime  // elapsed
audio.duration     // total
audio.paused       // isPaused
```

## Аудио-конвейер (FFT для визуализатора)

```
suno.com (вкладка)
  └── offscreen.js      ← Web Audio API: analyser (FFT) + delayNode (звук в колонки)
        └── chrome.runtime.sendMessage(AUDIO_DATA)
              └── background.js   ← пересылает в WS (порт 6969, fast path)
                    └── suno_rpc.py  ← ретранслирует в Broadcast API (порт 6970)
                          └── Electron-оверлей (python/визуал/suno-overlay)
```

`offscreen.js` захватывает звук вкладки через `chrome.tabCapture` (см. `background.js:startAudioCapture`) и строит Web Audio граф:
- `source → analyser` — FFT, **без задержки**, сразу.
- `source → delayNode → audioCtx.destination` — то, что реально слышно в колонках, **с задержкой**.

**`TRACK_UPDATE` должен приниматься только от захваченной вкладки (2026-08-09).** `content.js` работает независимо на КАЖДОЙ открытой вкладке suno.com — даже фоновой, на паузе — и шлёт `TRACK_UPDATE` раз в 2с (см. AI_GUIDE.md выше, «Структура передаваемых данных»). Раньше `background.js` принимал это сообщение от любого отправителя без проверки — если у пользователя открыто больше одной вкладки suno.com, их обновления перебивали друг друга в случайном порядке, и в Discord/оверлее мелькал то один трек, то другой, без всякой связи с тем, что реально играет (жалоба пользователя: «в Discord опять не тот трек», ошибочно принятая за дубль процессов `SunoRPC.exe` — на деле процесс был один, см. ниже). Исправлено: `background.js` принимает `TRACK_UPDATE` только от `sender.tab.id === capturedTabId`, пока `capturedTabId` не `null` — первая вкладка, от которой пришло сообщение, "застолбляет" трекинг (аудио и метаданные теперь всегда об одной и той же вкладке — раньше это не гарантировалось даже без багa с перебиванием). Освобождается автоматически в `chrome.tabs.onRemoved`/`onUpdated` при закрытии/перезагрузке captured-вкладки — новая вкладка сможет взять на себя трекинг только после этого.

**Зачем задержка звука.** Конвейер offscreen → background → Python → Electron → рендер занимает какое-то время (сглаживание в оверлее, WS-хопы, `setInterval(50мс)` в offscreen.js для сэмплирования FFT). Без компенсации звук, который слышит пользователь, опережает визуальную реакцию — маска в оверлее «догоняет» уже отзвучавший бас. Задержка `delayNode` сдвигает то, что слышно, чтобы оно совпало по времени с готовой отрисовкой.

**Авто-подстройка задержки (2026-08-08).** Величина задержки не захардкожена — `background.js` раз в 2с шлёт `PING` с меткой времени через уже открытый control-WS (порт 6969), `suno_rpc.py` сразу отвечает `PONG` (см. `handle_client()`, fast path рядом с `AUDIO_DATA`), и `background.js` берёт `RTT/2` как оценку задержки конвейера + фиксированный `RENDER_BUFFER_MS` (грубая поправка на сглаживание/рендер в оверлее — Electron не участвует в замере напрямую, обратного канала оттуда нет). Результат сглаживается через EMA и шлётся в offscreen.js как `SET_DELAY`, где `delayNode.delayTime` меняется плавно через `setTargetAtTime` (резкое изменение задержки вызывает щелчок/подскок высоты звука).

**`RENDER_BUFFER_MS` — это ОЦЕНКА, не измерение, и зависит от личных настроек пользователя.** Он не учитывает конкретные `smoothIn`/`smoothOut` оверлея (сколько реально времени занимает сходимость сглаживания до заметной глазу величины) — эта информация недоступна расширению. Поэтому у пользователя почти наверняка останется небольшая систематическая ошибка. Для этого в попапе расширения (`popup.html`/`popup.js`) есть ползунок **«Задержка звука (визуал)»** (`-200..+400мс`, хранится в `chrome.storage.local` как `audioDelayOffsetMs`) — ручная добавка поверх авто-расчёта, применяется сразу через `SET_DELAY_OFFSET` → `background.js` пересчитывает и шлёт `SET_DELAY`. Если пользователь жалуется, что звук всё ещё опережает/обгоняет визуал даже после авто-подстройки — не увеличивай/уменьшай `RENDER_BUFFER_MS` вслепую ещё раз, направь его двигать этот ползунок самому (он один может услышать, насколько именно не совпадает).

⚠️ **После правки `offscreen.js`/`background.js`/`suno_rpc.py` нужно и обновить расширение (`chrome://extensions` → 🔄), и перезапустить `suno_rpc.py`** — оба не подхватывают изменения на лету, старый код продолжает работать в уже запущенном процессе (если это скомпилированный `.exe` из `python/dist/`, а не сам `.py` — нужно ещё и пересобрать: `pyinstaller suno_rpc.spec`, предварительно закрыв старый процесс, иначе PyInstaller не сможет перезаписать файл — `PermissionError`).

**`analyser.smoothingTimeConstant` — не делать его высоким.** У `AnalyserNode` есть собственное встроенное экспоненциальное сглаживание FFT (дефолт Web Audio API — 0.8), которое применяется ДО того, как данные вообще покидают offscreen-документ — раньше, чем любые настройки Атака/Релиз в оверлее их увидят. Если тут поставить высокое значение, транзиенты (удары баса, кик-драм) размываются на входе, и никакая последующая настройка сглаживания в оверлее их уже не восстановит — ползунки становятся бессмысленными. Держать низким (сейчас `0.2`) и доверять сглаживание конфигурируемым `smoothIn`/`smoothOut` в оверлее.

**Бас/мид/хай считаются в Гц, не по индексу массива (2026-08-08).** Раньше сырой `fft`-массив (64 бина, `FFT_SIZE=128`) гонялся по всему конвейеру, и оверлей сам делил его на четверти ПО ИНДЕКСУ — при 48кГц это давало "бас"-полосу 0-6кГц вместо настоящих 20-250Гц, так что вес "бас" в настройках реагировал на что угодно в нижней половине спектра (в т.ч. снейр, вокал), а не именно на бас. Теперь `offscreen.js` сам считает `bass`/`mid`/`high` (границы `BASS_MAX_HZ=250`/`MID_MAX_HZ=4000`, переведённые в индекс бина через РЕАЛЬНУЮ `audioCtx.sampleRate` — она не всегда 48кГц) и шлёт уже готовые 0..1 значения; `FFT_SIZE` поднят до `1024` для разрешения, достаточного чтобы бас не размазывался по соседним бинам. Меняешь границы полос — меняй только в `offscreen.js`, `overlay.html`'s `updateMaskFFT()` их больше не вычисляет, только взвешивает готовые значения через `audioCfg.bassWeight/midWeight/highWeight`.

**«Выйти» в трее/веб-UI не завершал процесс — только поток иконки (2026-08-09).** `quit_app()` (вызывается и из `pystray`-меню «Выйти», и из `Api.quit_app` веб-интерфейса — оба НЕ главный поток: колбэк pystray выполняется в потоке `tray_icon.run()`, JS-мост webview — в своём собственном) заканчивался на `sys.exit(0)`. В CPython `sys.exit()`/`SystemExit` из НЕ главного потока убивает только этот поток, а не весь процесс — `tray_icon.stop()` и `rpc.clear()` перед ним успевали отработать (значок пропадал из трея, Discord presence чистился), но WebSocket-серверы и Discord RPC на других потоках продолжали жить дальше «призраком»: без иконки, невидимо для пользователя, но полностью рабочим (жалоба: «визуализация работает, а самого приложения в трее нет» — сначала выглядело как баг с дублирующимися процессами, на деле оказалось этим). В логе (`%APPDATA%\SunoRPC\suno_rpc_console.log`) это видно как `👋 Остановка...` сразу за которым — трейсбек pystray `An error occurred when calling message handler` → `SystemExit: 0` в `quit_app`. Исправлено на `os._exit(0)` — гарантированно убивает весь процесс из любого потока; безопасно здесь, так как ручная очистка (`rpc.clear()`/`tray_icon.stop()`/`window.destroy()`) уже выполнена строками выше. Подтверждено изолированным тестом: `sys.exit()` из фонового потока — процесс живёт дальше; `os._exit()` — процесс гарантированно и немедленно завершается.

**`spectrum` — настоящий 24-полосный спектр для эквалайзера (2026-08-09).** Добавлено для стиля «Полоски» у независимых волн (см. CLAUDE.md, «Независимые волны») — `buildSpectrumBins()` в `offscreen.js` делит диапазон 40Гц..Nyquist на `SPECTRUM_BARS=24` полос ПО ЛОГАРИФМИЧЕСКОЙ шкале (как в реальных эквалайзерах — иначе бас сожмётся в 1-2 крайних бина, а высокие займут половину графика), границы каждой полосы в бинах считаются один раз в `startCapture()` от реальной `sampleRate` и переиспользуются каждый кадр. Протокол `AUDIO_DATA` теперь `{bass, mid, high, volume, spectrum}` на всех хопах — `spectrum` довешен ПОВЕРХ `bass/mid/high`, не заменяет их (те три скаляра всё ещё нужны маске обложки и стилям «Линия»/«Радиальная» у волн). `overlay.html` сглаживает `spectrum` поэлементно в `spectrumSmooth[24]`, тем же `smoothToward()`.

**Грубость частотных «корзин».** `FFT_SIZE = 128` → 64 бина на весь диапазон 0–22кГц (~344Гц/бин при 44.1кГц). `updateMaskFFT()` в оверлее делит массив на 4 равные по ИНДЕКСУ четверти (bass/mid/himid/high) — это не то же самое, что деление по реальным частотам: «bass»-четверть (бины 0–15) на деле покрывает 0–5.5кГц, а не только суббас. Увеличение `FFT_SIZE` дало бы точнее по частоте, но хуже по времени (компромисс FFT) — резкость реакции на ритм важнее точности полосы, поэтому не увеличивать `FFT_SIZE` не подумав об этом трейд-оффе.

## Ограничения Discord Rich Presence

- Обновление не чаще **1 раза в 15 секунд** (лимит API) — настраивается в `UPDATE_INTERVAL`
- `large_image` принимает: загруженные арт-ассеты в Developer Portal **или** прямые URL
- CDN Suno (`cdn2.suno.ai`) Discord принимает — проверено
- Если обложка не отображается: подождать 1-2 минуты (Discord кеширует), либо загрузить ассет вручную
- Прогресс-бар работает только при воспроизведении (не на паузе) — это ограничение Discord

### Связь с Discord рвётся молча — её обязан поднимать сторож

Пайп Discord закрывается не только когда клиент выключают: он рвётся при
перезапуске и автообновлении Discord и при выходе компьютера из сна. Разрыв
ничем себя не выдаёт — pypresence узнаёт о нём только в момент отправки, и
падает при этом та отправка, которая случилась первой после разрыва.

До 2026-08-31 из этого состояния приложение не выходило само. `update_presence()`
пробовала переподключиться прямо в `except`, а `apply_idle_presence()` просто
писала в журнал `⚠️ Ошибка шаблона ожидания: The pipe was closed` — и оставляла
мёртвый объект `rpc` жить дальше. Дальше не происходило ничего: `state["discord"]`
оставался `True`, интерфейс показывал «Discord подключён», а активности в профиле
не было вообще. Симптом со стороны пользователя — «Discord не видит активность,
перезапуск и приложения, и Discord не помогает»; перезапуск и не мог помочь, потому
что каждый новый запуск Discord рвал пайп заново, а единственным выходом было
ручное «Переподключить».

Как устроено сейчас:

- `_mark_discord_lost()` — единая реакция на любую неудачную отправку: закрывает
  соединение, ставит `rpc = None`, снимает `state["discord"]` (индикатор перестаёт
  врать) и сбрасывает `idle_shown`/`last_update`.
- `discord_watcher()` — фоновая задача рядом с `idle_watcher()` в общем `gather`,
  раз в `DISCORD_RETRY_SEC = 15` поднимает связь, пока не поднимет. Она же чинит
  запуск приложения раньше Discord (автозагрузка Windows) — раньше одноразовый
  connect при старте оставлял `rpc = None` до конца сеанса.
- `connect_discord(quiet=…)` — ретраи сторожа не пишут в журнал одну и ту же
  ошибку каждые 15 секунд, сообщение появляется один раз на серию неудач.
- `apply_idle_presence()` возвращает `bool`, и `idle_watcher` ставит `idle_shown`
  только на успешной отправке. Иначе оборванная связь считалась бы показанным
  шаблоном, и повтора не случилось бы уже никогда.
- Шаблон ожидания переотправляется раз в `IDLE_REFRESH_SEC = 60`
  (`idle_shown_at`). Это единственная отправка в тишине, а значит единственная
  возможность вообще заметить обрыв, пока музыка не играет; заодно возвращает
  активность, потерянную перезапуском Discord. Раз в минуту — при лимите Discord
  в пять обновлений за двадцать секунд это безопасно, и это НЕ возврат к багу
  «шаблон уходит каждые `IDLE_CHECK_SEC` секунд»: проверка по-прежнему каждые 5
  секунд, отправка — раз в минуту.
- Переподключение (и ручное, и автоматическое) сбрасывает `idle_shown` и
  `last_update`. Без этого после успешного «Переподключить» в режиме ожидания
  активность оставалась пустой до следующего трека — проверено живьём.

Внутри `update_presence()` поднимать связь нельзя: `connect` висит до
`DISCORD_CONNECT_TIMEOUT` секунд и подвесил бы вместе с собой обработку
сообщений расширения. Поэтому там только `_mark_discord_lost()`, а подключение —
дело сторожа.

## Живучесть suno-расширения

Chromium выгружает service worker расширения примерно через 30 секунд простоя,
унося с собой WebSocket. Обычно worker будит `content.js` со своим интервалом в
2 секунды, но у ФОНОВОЙ вкладки браузер душит таймеры — сообщения приходить
перестают, и worker умирает. В логе сервера это выглядит как «расширение
подключилось / отключилось» каждые полминуты, а в Discord — как чередование
трека и шаблона ожидания, хотя музыка играет всё это время.

Лечится будильником `chrome.alarms` (`periodInMinutes: 0.5`, разрешение
`alarms` в манифесте): он будит worker независимо от состояния вкладки, а
обработчик проверяет сокет и переподключается. Полагаться на `setInterval`
внутри worker'а нельзя — таймеры умирают вместе с ним.

## Грабли второго источника

- **Firefox не выпускает `ws://` из расширения — это причина, по которой
  YouTube-расширение ходит по HTTP.** Контекст расширения (`moz-extension://`)
  считается защищённым, и небезопасный WebSocket из него Firefox либо блокирует
  молча, либо повышает до `wss://`. Проверено на Firefox 154 сырым TCP-слушателем:
  на `ws://127.0.0.1` прилетал TLS ClientHello с ALPN `h2,http/1.1`, соединение
  закрывалось с кодом 1006, и расширение выглядело установленным, но мёртвым.
  Отключение `dom.security.https_first` не помогает — запрос тогда просто не
  уходит вовсе. При этом обычный `fetch` на тот же localhost проходит: проверка
  `fetch("http://127.0.0.1:6969/")` вернула 426 Upgrade Required от самого
  websockets-сервера. Не пытайся «починить» это ретраями или сменой хоста на
  127.0.0.1 — оба варианта проверены и ведут себя одинаково.

  **Но границы этого ограничения шире, чем написано выше, и до конца не
  выяснены.** 2026-09-01 владелец проекта сообщил, что suno-расширение из
  каталога Mozilla (`suno-discord-rpc` 1.4.0) в Firefox работает: сервер видит
  и трек, и время. В его пакете именно `ws://localhost:6969` из фонового
  скрипта — то, что по опыту выше работать не должно. Отличий от подопытного
  YouTube-расширения два: `manifest_version` 2 против 3 (обычная фоновая
  страница вместо service worker) и другая версия Firefox у пользователя.
  Пока не установлено, что из этого решает, НЕ пиши в документации и в
  интерфейсе «в Firefox не работает» — это опровергнуто живым запуском. Что в
  Firefox действительно недоступно, так это сбор звука: `offscreen` и
  `tabCapture` есть только в Chromium, поэтому там нет FFT, а с ним оверлея и
  «волн». Активность в Discord при этом живёт.
- **Обложка YouTube — `hqdefault`, а не `maxresdefault`.** Последнего у части
  видео просто нет, и Discord показывал бы пустую обложку вместо превью.
- **Во время рекламы данные слать нельзя.** `<video>` в этот момент проигрывает
  ролик рекламодателя: длительность и позиция относятся к нему, а название на
  странице остаётся от настоящего видео — в Discord поехал бы таймкод.
  `content.js` пропускает обновление, пока висит `.ad-showing`.
- **YouTube — SPA.** Переход к другому видео не перезагружает страницу и не
  перезапускает content-скрипт; поэтому `tick()` каждый раз перечитывает URL и
  DOM заново, а уход со страницы видео отдельно сообщается как `YT_GONE` —
  иначе сервер ещё 10 секунд считал бы источник живым.
- **Вкладок YouTube обычно несколько**, и content.js работает в каждой, включая
  фоновые с паузой. Выбор текущей делает `pickActiveTab()` в background.js —
  та же болезнь, что когда-то лечили в suno-расширении через `capturedTabId`.
- **Перемотка назад сбрасывает опорную позицию ДО проверки «просмотр засчитан».**
  Если засчитать ещё не успели, а зритель отмотал ролик в начало, старая
  (большая) позиция осталась бы висеть, и время до неё повторно не
  накапливалось бы — просмотр молча недосчитывался. В `suno_stats` тот же
  сброс сделан только для уже засчитанных треков.
- **Control API проверяет заголовок `Origin`.** Порт 6972 слушает только
  127.0.0.1, но на localhost может зайти и любая открытая вкладка: простые
  POST-запросы уходят на сервер даже без CORS — браузер прячет только ОТВЕТ,
  а побочный эффект уже случился. Поэтому `origin_guard` пропускает запросы
  без Origin (интерфейс Electron, curl) и с `moz-extension://` /
  `chrome-extension://`, а обычные страницы получают 403. Если добавляешь
  маршрут в control API, помни, что он автоматически попадает под ту же защиту.
- **Конфиг пишется в UTF-8 явно.** Раньше `open(CONFIG_FILE, "w")` брал
  системную кодировку, и файл с кириллическими подписями кнопок оказывался в
  cp1251. С появлением секции `[buttons_youtube]` (подписи «Открыть видео»,
  «Мой канал») это стало заметно сразу. Чтение переживает старые cp1251-файлы.

## Шаблон ожидания

Когда `pick_active_source()` возвращает None, показывается настраиваемый шаблон
из секции `[idle]` конфига — или активность снимается, если шаблон выключен.
До него в Discord навсегда зависал последний трек: путь обновления активности
событийный, он выполняется только когда расширение прислало данные, а когда
присылать перестают, не срабатывает ничего. Поэтому нужен **фоновый цикл**
`idle_watcher()` (раз в `IDLE_CHECK_SEC = 5`), а не обработка в общем пути.

- **Ожидание считается от прекращения ВОСПРОИЗВЕДЕНИЯ, а не от исчезновения
  источников.** Первая версия ждала, пока `pick_active_source()` вернёт None, —
  и шаблон не наступал никогда: расширение продолжает слать данные каждые 2
  секунды, пока вкладка открыта, даже если там пауза. Теперь есть `no_play_since`
  (обновляется в `_refresh_play_clock()`) и `idle_due()` с отсрочкой
  `idle.after_seconds` (по умолчанию 30 с, 0 — сразу по паузе).
- **Выбор источника при общей паузе — липкий.** Если ни один источник не играет,
  `pick_active_source()` сначала пробует оставить тот, что показывается сейчас.
  Раньше сравнивалось время последнего сообщения, и при двух открытых вкладках
  на паузе (у обеих `playing_at` = 0) активность в Discord непрерывно мигала
  между Suno и YouTube — они шлют по очереди каждые 2 секунды.
- **Сбрасывать `idle_shown` можно только когда ожидание больше не актуально**
  (`if idle_shown and not idle_due()`). Без второго условия флаг обнуляло любое
  входящее обновление, включая приходящие раз в две секунды от источника на
  паузе: сторож считал шаблон непоказанным и слал его в Discord заново каждые
  `IDLE_CHECK_SEC` секунд.
- **`SOURCE_STALE_SEC` не меньше 15 секунд.** Service worker расширения в
  Chromium выгружается по таймауту простоя, и короткие провалы в потоке данных
  — норма, а не признак того, что музыку выключили.
- **`process_source_update()` не трогает presence, пока `idle_due()`.** Иначе
  приходящие раз в две секунды обновления поставленного на паузу трека затирали
  бы шаблон сразу после того, как сторож его выставил.
- `apply_idle_presence()` намеренно отдельна от `update_presence()`: та
  троттлится по `UPDATE_INTERVAL` и завязана на данные источника, а здесь нужен
  разовый показ. Флаг `idle_shown` не даёт переставлять активность каждые 5 с.
- Возврат источника сбрасывает `idle_shown` и `last_update` — иначе трек
  появился бы поверх шаблона с задержкой до `UPDATE_INTERVAL`.
- Плейсхолдеры (`{tracks}`, `{hours}`, `{last_track}`, `{last_artist}`)
  подставляются простым `str.replace`, а НЕ `str.format`: случайная фигурная
  скобка в тексте пользователя роняла бы `format` KeyError'ом и весь шаблон.
- Картинка задаётся ссылкой или ключом ассета из Discord Developer Portal.
  Локальные файлы приложения не годятся — Discord тянет изображение сам и до
  диска пользователя не достаёт.
- **`Api.save_config` отвергает пустой payload.** Раньше нераспарсенное тело
  запроса (битый JSON, чужая кодировка) превращалось в `{}`, и сохранение
  переписывало КАЖДЫЙ ключ пустой строкой — одна неудачная отправка стирала
  Client ID, кнопки и шаблон разом. Признак сбоя — отсутствие `websocket_port`:
  форма интерфейса всегда шлёт полный набор полей.

## Иконки приложения

Четыре варианта («Плеер»/«Бойкиссер», каждый с прозрачным и сплошным углом).
Исходники — `desktop/src/icons/source/`, наборы под них генерирует
`build-icons.py` в `desktop/src/icons/variants/`. Запускать после замены
исходной картинки; результат хранится в репозитории, чтобы сборка не требовала
Pillow.

Три места, и ведут они себя по-разному:

| Где | Откуда берётся | Меняется на лету |
|---|---|---|
| Трей | `<slug>-tray-<состояние>.ico` | да |
| Окно, кнопка на панели задач, Alt+Tab | `<slug>.ico` через `win.setIcon()` | да |
| Файл .exe в проводнике, закреплённый ярлык | зашито в exe при сборке | **нет** |

- **Состояние трея свёрнуто в цвет точки.** Раньше иконка трея рисовалась
  кодом (`make_icon` в Python) и показывала play/pause формой значка плюс
  точку подключения к Discord. На готовой картинке пользователя глиф не
  нарисуешь, поэтому оба признака кодирует одна точка, которую дорисовывает
  `build-icons.py`: зелёная — Discord подключён и идёт воспроизведение,
  жёлтая — подключён, но пауза, серая — Discord недоступен. Точка идёт с
  тёмной обводкой: без неё зелёное терялось на белой шерсти «бойкиссера».
- **Выбор варианта хранится у Electron, а не в конфиге бэкенда**
  (`ui-settings.json` в `app.getPath('userData')`, то есть
  `%APPDATA%\suno-rpc-desktop`). Трей рисуется сразу при запуске, до того как
  бэкенд поднимется, — читай настройку до создания окна и трея, иначе иконка
  будет меняться на глазах через пару секунд после старта.
- **Иконку .exe прописывает `desktop/set-exe-icon.js`, а не electron-builder.**
  Штатно это делает он сам, но у нас отключён `signAndEditExecutable` (см. ниже
  про winCodeSign), а вместе с ним отключается и rcedit — exe оставался с
  иконкой Electron. Поэтому `npm run dist` разбит на три шага: сборка папки
  (`--dir`), прописывание иконки, упаковка установщика (`--prepackaged`).
  Пакет `rcedit` версии 5 — ESM и экспортирует именованную функцию:
  `const { rcedit } = require('rcedit')`, иначе «rcedit is not a function».

## Окно, автозапуск и полоса заголовка

Всё это живёт в главном процессе Electron (`desktop/src/main.js`) и хранится в
том же `ui-settings.json`, что и выбор иконки, — то есть в
`%APPDATA%\suno-rpc-desktop`, а не в конфиге бэкенда. Причина та же, что у
иконки: окно создаётся и показывается в первые миллисекунды, а бэкенд отвечает
только через пару секунд, и спрашивать у него, показывать ли окно, поздно.

Переключатели (карточка «Окно и запуск» на вкладке «Настройки»):
`autoLaunch`, `startMinimized`, `closeToTray`, `minimizeToTray`, `alwaysOnTop`,
`traySingleClick`, `rememberBounds` плюс сохранённые `bounds`. Применяются
**сразу при клике**, по одному ключу через `set_window_setting` — кнопка
«Сохранить» на той же вкладке относится только к конфигу бэкенда, и путать эти
два механизма не надо.

- **`loadUiSettings()` мержит файл с `DEFAULT_UI_SETTINGS`, а не возвращает
  прочитанное целиком.** Файл мог быть записан версией, где половины ключей ещё
  не было; без мержа `uiSettings.closeToTray` оказался бы `undefined`, и ✕ молча
  начал бы закрывать приложение вместо сворачивания в трей.
- **Автозапуск — `app.setLoginItemSettings` с аргументом `--autostart`.** Этот
  аргумент нужен, чтобы отличить старт вместе с Windows от ручного: системный
  запуск всегда уходит в трей независимо от `startMinimized`. В режиме
  разработки регистрация пропускается (`app.isPackaged`) — иначе в реестр попал
  бы путь к `electron.exe` без папки проекта, и система поднимала бы пустой
  Electron. Флажок при этом сохраняется и заработает в собранном приложении;
  интерфейс узнаёт об этом по `autoLaunchSupported` и подменяет подсказку.
- **`minimize` требует `preventDefault()`.** Без него окно сначала честно
  сворачивается, и после `hide()` в трее остаётся невидимая свёрнутая копия:
  следующий `show()` поднимает её уже развёрнутой.
- **Сохранённую геометрию нельзя применять вслепую.** Монитор, на котором окно
  стояло, могли отключить. `savedWindowBounds()` проверяет, попадает ли точка
  внутри полосы заголовка в `workArea` хоть одного дисплея, и если нет —
  оставляет только размер, отдавая позицию системе. Запись троттлится на 500 мс
  (`resize`/`move` летят десятками за одно перетаскивание) и делается ещё раз
  синхронно в `close`, до `hide()`: у скрытого окна координаты уже бессмысленны.

**Полоса заголовка нарисована нами.** `titleBarStyle: 'hidden'` +
`titleBarOverlay` в `createMainWindow()`: системной полосы нет, её место
занимает `.titlebar` из `index.html`, а кнопки свернуть/развернуть/✕ рисует сам
Windows поверх правого края в заданных цветах — работают и Snap Layouts, и
подсветка при наведении, но цвет уже не зависит от темы и акцента пользователя.
Своих кнопок окна в разметке быть не должно.

- Цвет продублирован в двух местах и должен совпадать: `TITLEBAR_COLOR` /
  `TITLEBAR_HEIGHT` в `main.js` (кнопки) и `--tb` / `--tb-h` в `index.html`
  (полоса, обводка окна). Разъедутся — будет видно стыком двух оттенков
  фиолетового у правого края.
- Он **намеренно константа, а не настройка**: окно должно совпадать по цвету с
  иконкой приложения. Обводка окна тоже своя (`border` на `body`), потому что
  цвет системной рамки задаёт Windows по акценту пользователя и подменить его
  из Electron нельзя.
- **Тянуть окно можно только за `.tb-drag`, ширина которого —
  `env(titlebar-area-width)`.** Это ширина свободной части полосы, её сообщает
  странице Windows Controls Overlay. Растянешь drag-регион на всю ширину —
  перетаскивание перехватит клики по ✕.
- Оверлей `#backend-down` позиционируется от `var(--tb-h)`, а не `inset:0`:
  иначе он ложится поверх полосы заголовка и окно перестаёт таскаться ровно
  тогда, когда что-то сломалось.
- Окно статистики полосу не наследует: оно грузит HTML-отчёт, сгенерированный
  Python, — своей разметки заголовка там нет, и с `titleBarStyle: 'hidden'` его
  просто нечем было бы таскать.

## Расширения внутри установщика

Расширения вложены в установщик готовыми распакованными папками, чтобы
пользователю не пришлось ничего скачивать: `fetch-extensions.js` клонирует три
репозитория в `desktop/extensions-bundle/`, а `extraResources` в
`package.json` кладёт эту папку в сборку как `resources/extensions`. Шаг встроен
в `npm run dist`, отдельно — `npm run extensions`.

**Берём из GitHub, а не из соседних папок на диске, и это принципиально.**
Копия `audio-fx-extension`, лежавшая когда-то внутри этого репозитория, отстала
от рабочей на восемь минорных версий (1.0.0 против 1.8.2), и никто не замечал,
пока не полез сверять файлы. Опубликованный репозиторий — единственный источник
правды; скрипт печатает версию каждого расширения вслух, чтобы расхождение было
видно сразу. Цена — без сети установщик с расширениями не собрать.

**Установить расширение ЗА пользователя приложение не может, и пытаться не надо.**
Chromium с 2018 года блокирует установку мимо магазина: реестровый ключ
`HKLM\SOFTWARE\Google\Chrome\Extensions` с путём к локальному `.crx` больше не
срабатывает — расширение либо не ставится, либо тут же отключается. Firefox не
грузит неподписанные XPI вовсе. Обойти это можно только политиками предприятия
(`ExtensionInstallForcelist` + самохостинг `update.xml`), но тогда расширение
становится принудительным и неудаляемым, нужны админ-права, а Opera GX — браузер
по умолчанию у автора — политики Chromium поддерживает частично. Поэтому вкладка
«🧩 Расширения» показывает путь и открывает страницу браузера, а установку
оставляет пользователю.

- **Страницу расширений нельзя открыть через `shell.openExternal`.** Схемы
  `chrome://`, `edge://`, `opera://` в системе не зарегистрированы, и Windows на
  них ругается. Браузер принимает такой адрес аргументом командной строки —
  `spawn(exe, [page], { detached: true })`, обязательно с `unref()`, иначе
  браузер станет дочерним процессом приложения и умрёт вместе с ним.
- **Пути к браузерам записаны через ПРЯМЫЕ слэши.** Windows и Node принимают их
  наравне с обратными, зато в строковом литерале нечего экранировать. На
  обратных это уже ломалось: пара `\\` потерялась при генерации файла, `\firefox`
  превратился в перевод формата плюс `irefox`, и все браузеры молча пропали из
  списка — без единой ошибки в консоли, просто пустой массив.
- **Проверять приложение при работающей установленной копии не выйдет.**
  `requestSingleInstanceLock()` отдаст `false`, и запуск из исходников молча
  завершится с кодом 0 — ни окна, ни ошибки, только строка про DevTools. Для
  живого теста запускай с `--user-data-dir=<временная папка>`: блокировка станет
  своей, бэкенд не поднимется (порты заняты установленной копией), но вкладки, не
  зависящие от бэкенда, проверяются нормально.

## Грабли связки Electron ↔ Python

Всё ниже — реальные баги этого перехода, каждый ловился живым запуском, а не
чтением кода.

- **Мост нельзя называть `window.api`.** `contextBridge.exposeInMainWorld('api',…)`
  создаёт неконфигурируемое свойство глобального объекта, а в скрипте страницы
  было `let api = null`. Объявление падало с `SyntaxError: Identifier 'api' has
  already been declared` — на этапе ПАРСИНГА, то есть весь инлайн-скрипт
  index.html молча не выполнялся: разметка рисовалась, `window.api` работал, а
  ни одной функции страницы не существовало, и окно вечно показывало «Ожидание
  трека». Мост называется `sunoApi` именно поэтому.
- **stdout бэкенда обязан быть UTF-8.** Когда Python пишет в пайп родителя, он
  берёт кодировку из системной кодовой страницы Windows (здесь cp1251), а логи
  в этом проекте состоят из эмодзи. Первый же `log_event` убивал процесс
  `UnicodeEncodeError`'ом до старта серверов. Лечится `sys.stdout.reconfigure(
  encoding="utf-8")` в начале `suno_rpc.py` — не удаляй эту ветку.
- **Слежение за родителем — только по флагу `--watch-stdin`.** Бэкенд выходит,
  когда stdin отдаёт EOF (так он не остаётся «призраком» после падения
  Electron). Но если запустить `python suno_rpc.py` там, где stdin не подключён
  к живому писателю (фоновая задача, перенаправление из nul), EOF приходит
  сразу, и процесс выходит с кодом 0 через доли секунды — снаружи это выглядит
  как «сервер не поднимается», без единой строчки ошибки.
- **Discord не должен блокировать старт.** `AioPresence.connect()` ходит в
  именованный пайп Discord и при незапущенном клиенте висит, а не падает.
  Раньше это было незаметно (окно и трей жили в главном потоке), теперь
  интерфейс ждёт ответа control API, поэтому подключение вынесено в фоновую
  задачу и ограничено `DISCORD_CONNECT_TIMEOUT`.
- **`signAndEditExecutable: false` в `desktop/package.json` — вынужденная мера.**
  Чтобы подписать и отредактировать exe, electron-builder качает пакет
  `winCodeSign`, внутри которого лежат macOS-симлинки. Их распаковка на Windows
  требует прав администратора или включённого режима разработчика, иначе сборка
  падает на `Cannot create symbolic link … libcrypto.dylib` (на этой машине
  режим разработчика выключен). Флаг пропускает этот шаг, ценой того, что у
  `Suno RPC.exe` остаётся стандартная иконка Electron в проводнике — иконка
  окна, ярлыков и установщика берётся из `src/icons/app.ico` и не страдает.
  Включишь режим разработчика в параметрах Windows — флаг можно убрать.
  Заранее распаковывать кеш вручную бесполезно: имя папки случайное на каждый
  запуск сборки.
- **`cwd` для бэкенда задаёт `backendCommand()`, а не `spawn` напрямую.** В
  собранном приложении папки `python/` рядом нет, а `__dirname` указывает
  внутрь `app.asar` — `spawn` с несуществующим `cwd` падает с ENOENT ещё до
  запуска бэкенда, и приложение показывает «Бэкенд не отвечает».
- **Прокси Hiddify ломает и Electron.** `app.commandLine.appendSwitch(
  'no-proxy-server')` в начале `main.js` — обязателен, иначе запросы к
  127.0.0.1:6972 уходят в прокси. При отладке через CDP из Python не забывай
  `ProxyHandler({})` / `--noproxy '*'`.

## Типичные баги и решения

| Симптом | Причина | Решение |
|---|---|---|
| Название "Неизвестный трек" | Селектор берёт `.textContent` вместо `aria-label` | Парсить `aria-label` через regex |
| Обложка не та (чужой трек) | `querySelectorAll('img[src*="cdn2.suno.ai"]')` берёт первый попавшийся | Использовать `aria-label^="Playbar: Cover image"` |
| Обложка — аватарка профиля | Селектор попал на `img.rounded-full.h-9.w-9` (аватар юзера) | Использовать `aria-label^="Playbar: Cover image"` |
| `coverUrl` пустой | `coverImg.src` возвращает `""` в content script | Использовать `getAttribute('src')` |
| Статус не обновляется | `UPDATE_INTERVAL = 15` сек | Нормально, ждать |
| Расширение не видит аудио | Страница открыта до установки расширения | Обновить вкладку suno.com |
| Активности в Discord нет, хотя интерфейс пишет «Discord подключён» | Пайп закрылся (перезапуск/обновление Discord, сон системы), а мёртвый `rpc` жил дальше | Исправлено 2026-08-31: `_mark_discord_lost()` + `discord_watcher()`, см. «Ограничения Discord Rich Presence» |

## Как отлаживать селекторы

Открыть DevTools на suno.com (F12 → Console) и проверить:

```js
// Название
document.querySelector('a[aria-label^="Playbar: Title for"]')?.getAttribute('aria-label')

// Обложка
const img = document.querySelector('img[aria-label^="Playbar: Cover image"]');
console.log(img?.getAttribute('src'), img?.getAttribute('data-src'));

// Все img в плеере
document.querySelectorAll('img[src*="cdn2.suno.ai"]').forEach(i =>
  console.log(i.src.slice(0,80), i.getAttribute('aria-label'))
)
```

После правки `content.js`: `chrome://extensions` → кнопка обновления (🔄) → обновить вкладку suno.com.
